# Embedded Security Scanner

A custom, multi-domain Application Security scanner engineered for the UoA Sensory Map application. Built on Application Security Posture Management (ASPM) design principles, it unifies SAST, SCA, and IaC analysis into automated GitHub Actions CI/CD workflows, enriched with plain-language explanations and concrete code fix recommendations generated by an LLM model. 

# Scanning Methodology
The engine unifies three primary detection pillars feeding a centralized AI remediation pipeline:

SAST (Static Application Security Testing): Pure static code analysis of application source code via Abstract Syntax Tree (AST) pattern parsing.

SCA (Software Composition Analysis): Open-source dependency auditing against known Common Vulnerabilities and Exposures (CVEs).

IaC (Infrastructure as Code): Configuration manifest auditing (delegated to Checkov) to detect cloud and pipeline misconfigurations.

Out of Scope: Dynamic analysis methodologies (DAST, IAST) are intentionally excluded, as they require an active, instrumented runtime application environment.

## Outputs & Reporting

Rather than outputting raw scanner logs, the tool translates technical vulnerability findings into accessible reports so that any stakeholder—not just senior developers—can understand and act on them.

For every detected vulnerability, the output includes:

Security Context ("Why It Matters"): A 2–3 sentence plain-language explanation of the security risk and potential business/technical impact.

Concrete Fix Guidance: Language-native code snippets and actionable instructions highlighting the exact lines of code that need modification.

## Scanner design & Connectivity

The scanner consists of three distinct analysis engines feeding a shared, resilient AI enrichment layer:

| Pillar | Focus Area | Connectivity / Execution Model |
| :--- | :--- | :--- |
| **SAST** | Source Code Flaws (Python) | Pure local execution — zero network overhead (AST parsing) |
| **SCA** | 3rd-Party Dependencies | Remote HTTPS REST API (OSV Database — unauthenticated) |
| **IaC** | Deployment & Infrastructure | Local CLI subprocess execution (`checkov` runner) |
| **AI Enrichment** | Contextual Fix Guidance & Summaries | Remote HTTPS API (`OpenRouter` — authenticated) |

### Pillar 1 — SAST: Rule-based scanner (Python, AST parsing)

Implements 19 detection rules mapped directly against core cybersecurity frameworks:

- OWASP Top 10 (2025)

- OWASP Code Review & Testing Guides

- CWE (Common Weakness Enumeration)

**Connectivity:**
N/A Pure local execution — (AST parsing)

**How it works:**

1. Every `.py` file in the project is parsed into an AST (Abstract Syntax Tree) — Python's own internal representation of the code's structure
2. Each rule walks the tree looking for a specific dangerous pattern — a hardcoded secret, a call to `eval()`, a missing permission check, etc.
3. Matched patterns are reported as a Finding (rule ID, severity, attack technique, file/line, message, standard reference)
4. Findings are passed through an AI enrichment layer for a plain-language explanation and suggested fix, then formatted into a Markdown report and posted automatically as a PR comment

**Scope:** static analysis only — the scanner reads code structure, it never executes any of the code it scans. 

### Pillar 2 — IaC: Infrastructure as Code (Checkov)

Open-source IaC scanner (Checkov), configured to scan Terraform (`.tf`) files.

- The scanner invokes Checkov directly via Python's subprocess.run(["checkov", ...]) pipeline.

- Demonstration Setup: Because the UoA Sensory Map application utilizes PaaS deployment (Gunicorn + WhiteNoise) without active cloud IaC, static test fixtures (infra/demo.tf and tests_security_sast_sca_iac/fixtures/iac/) provide True Positive and True Negative test scenarios (Network Exposure, Encryption at Rest, and IAM Least Privilege) to validate end-to-end scanner execution.

**Connectivity:**

Checkov runs on Github Actions — no API, no network request, no credentials needed. The scanner invokes it via a subprocess call (`subprocess.run(["checkov", ...])`), the same as typing the command directly in a terminal.

**How it works:**

1. Checkov reads `.tf` files in the `infra/` folder and checks each resource block against its built-in rule library (network exposure, encryption, IAM permissions, and more)
2. Findings are captured from Checkov's own output and formatted consistently with the SAST and SCA pillars' reports
3. Runs as part of the same CI/CD pipeline, alongside SAST and SCA

**Scope:** UoA Sense Map does not currently provision infrastructure via Terraform (deployment is Gunicorn + WhiteNoise, no cloud IaC in place). A demonstration file (`infra/demo.tf`) provides 3 paired True Positive / True Negative configuration samples — network exposure, encryption at rest, and IAM least-privilege — to verify the scanning integration end-to-end. This file is not real infrastructure and should never be applied; it exists only to prove the tooling works correctly, so the pillar is ready to adopt if the project's deployment.

### Pillar 3 — SCA: Third-Party Dependency Scanning (OSV API)

Audits pinned open-source dependencies against Google’s OSV (Open Source Vulnerabilities) database, aligned with OWASP Top 10:2025 A03 – Software Supply Chain Failures.

- Parses requirements.txt to extract direct and transitive pinned packages alongside exact version specifiers.

- Queries the OSV REST API (https://api.osv.dev/v1/query) over HTTPS for matched CVE entries.

- Reachability Scope: Performs version-matched static analysis. It does not execute dynamic reachability analysis (verifying if vulnerable code paths are actively invoked), adhering to standard industry practice: upgrading vulnerable packages regardless of call-graph reachability.

**Connectivity:**

Connects to the OSV (Open Source Vulnerabilities) API over HTTPS — a free, public REST API, no authentication or API key required. The scanner sends one HTTP POST request per package (name, version, ecosystem) to `https://api.osv.dev/v1/query` and reads back any matched vulnerability records as JSON.

**How it works:**

1. Parse `requirements.txt` to extract each package name and pinned version
2. Query the OSV API for each package/version pair
3. Any matched CVE is reported as a Finding (package, version, CVE ID, severity), reusing the same reporting format as the SAST and IaC pillars
4. Runs as part of the same CI/CD pipeline, alongside SAST and IaC

**Scope:** scans every package listed in `requirements.txt` — this includes packages you directly chose (Django, DRF, Pillow, psycopg2-binary) as well as packages pulled in as dependencies of those but still explicitly pinned in the file (e.g. asgiref, sqlparse). Any package NOT listed in requirements.txt — i.e. resolved silently at install time without being pinned — falls outside this scanner's current scope, along with broader supply-chain integrity checks (unpinned versions, unhashed packages, CI Action pinning).Detecting these would require dynamic analysis (actually installing dependencies and inspecting the resolved environment), which is out of scope for this static analysis scanner.

Does NOT perform reachability analysis — a flagged vulnerability may exist in a code path the application never actually calls (e.g. a vulnerability in a debug/desktop-only feature of a library used purely for server-side image processing). Determining true exploitability would require tracing the application's call graph against each vulnerability's specific affected function(s), a form of analysis beyond this scanner's static, version-based approach. Standard industry practice (upgrade to patched version regardless of confirmed reachability) is still the recommended remediation.

**Note** IaC scanning was added beyond the project's original requirements to push the scanner's scope and difficulty further, as a third pillar alongside SAST and SCA. The deployment is PaaS-based, so the pillar targets real config where it applies — GitHub Actions workflows (`.github/workflows/*.yml`) — and validates its Terraform-checking logic against synthetic `.tf` fixtures (`tests_security_sast_sca_iac/fixtures/iac/`), using the same True Positive / True Negative approach applied to every other rule in the scanner.

### Pillar 4: AI enrichment

Transforms static alert outputs into accessible security explanations and concrete fix recommendations using hosted LLMs via OpenRouter.

Design notes:
- The AI layer is **additive**. If it fails (model busy, deprecated, or offline),the caller still has the original rule-based finding — detection never depends on it. Its role is to translate findings (vulnerabilities and recommendations) into plain language that everyone can understand, not only developers.
- Models are tried in priority order (fallback list). A "busy" model (429) is retried briefly; an "unavailable" model (402/404) is skipped immediately.
- The API key is read from the environment (`.env`), never hardcoded.

**Connectivity:**
OpenRouter hosted in a remote service. HTTP request through API request.

**How it works:**
```text
 [ Raw Findings ] ---> [ Build Structured Context Prompt ]
                                    |
                                    v
                     [ Try Primary Model Pipeline ]
                   (e.g., openai/gpt-oss-20b:free)
                                    |
             +----------------------+----------------------+
             | (200 OK)                                    | (429 / Timeout / Error)
             v                                             v
 [ Add AI Explanation ]                 [ Backoff & Cascade to Fallback ]
             |                               (qwen / llama models)
             |                                             |
             |                                             v
             |                              [ All Models Exhausted? ]
             |                                         |
             |                         +---------------+---------------+
             |                         | (Yes)                         | (Success)
             |                         v                               v
             |             [ Fallback to Static          [ Add AI Explanation ]
             |               Rule Output ]                             |
             +-------------------------+-------------------------------+
                                       |
                                       v
                        [ Render Final Output / Report ]
```

**Scope:**
Focuses on single-finding, localized contextual remediation (2–3 sentence business impact summary (why it matters) + language-native code fix (Concrete fix indicating specific line of code and file)) rather than repository-wide multi-file refactoring.

2. GitHub Actions Workflows

The scanner is integrated into repository operations using two automated GitHub Action workflows:

- Workflow 1: Synchronous Pull Request Gate (.github/workflows/pr-security-gate.yml)

Trigger: Automatically executes on any pull_request targeting main / master across all team branches.

Purpose: Acts as a blocking gate to prevent security regressions. If high or critical vulnerabilities are detected, the workflow fails, preventing unsafe code merges. 

Implementation Note: During evaluation, automated branch blocking was left unactivated due to project timeline constraints—as the scanner was engineered concurrently alongside the core UoA Sensory Map application. However, full automated PR blocking can be instantly toggled on via standard GitHub branch protection settings.

- Workflow 2: Asynchronous Repository Baseline (.github/workflows/baseline-security-scan.yml)

Trigger: On-demand (workflow_dispatch) or via a scheduled CRON trigger (e.g., weekly).

Purpose: Audits the entire codebase to establish a security baseline. Enriches identified vulnerabilities with LLM fix guidance and logs/updates comprehensive historical findings directly as native GitHub Issues.

## Design decisions

- Local model hosting (Ollama) was the initial plan but was blocked by the
development machine's device security policy (Smart App Control / Device Guard),
which cannot be disabled without reinstalling Windows. 
- The AI pillar therefore uses a hosted API via OpenRouter. This trades some data privacy (code is sent to a third party) for capability and easier CI integration — a documented compromise for a student project. 
- During evaluation, automated branch blocking was left unactivated due to project timeline constraints—as the scanner was engineered concurrently alongside the core UoA Sensory Map application. However, full automated PR blocking can be instantly toggled on via standard GitHub branch protection settings.
